How to make a change, e.g. upgrading software, change firewall config, modify switch ports

- Very common risk in the enterprise
- Often overlooked
- Need clear policies for frequency, duration, install process, rollback procedures

### Change approval process
- A formal process for managing change.
- *Example: A typical approval process*
	- Complete the request forms
	- Determine purpose of change
	- Identify scope of change
	- Scheduling date & time of change
	- Determine affected systems & impact
	- Analyze risk associated with change
	- Get approval from change control board
	- Get end-user acceptance after change

#### Ownership
- An individual needs to make a change
- The owner manages the process
	- Process updates given to owner, owner ensures process is followed & acceptable
- Usually, the actual change is implemented by IT, the process is just owned by some department

#### Stakeholders
- They'l want to have input on the change management process
- Change could include one individual or the whole company
	- *Example: Update software used for shipping labels*
		- Shipping receiving
		- Accounting reports
		- Product delivery timeframes
		- Revenue recognition

#### Impact Analysis
- Determine a risk value, risks can be minor or far-reaching
- What's the risk of NOT making the change?
	- Security vulnerability, application unavailability, unexpected downtime to other services

#### Test Results
- Sandbox testing environment
	- Use before making a change to production
	- Confirm the **backout plan**
		- The **backout plan** will revert back to the original version, before the change took place.
			- Usually easy, but some changes are very difficult.
			- Always have good backups

#### Maintenance window
- When is the change happening? Can be the most difficult part of process.
- During workday is probably not best. Overnights are often a better choice.
- Time of year may be a consideration (holiday season is very busy for retail).

#### Standard Operating Procedure
- Change management is critical
- The process should be well documented
- Changes to process are reflected in the standards

## Technical Change Management
- Put the change management process into action. Execute the plan.
-  Concerned with "what" needs to change.

#### Allow list / deny list
- Any app can be dangerous
- Security policy can control app execution with a list
- Allow list -> nothing runs unless it's approved. Very restrictive.
- Deny list -> nothing on the bad list can be executed. More flexible.

#### Restricted activities
- A change approval isn't permission to make any change.
- Scope may need to be expanded during the change window.
 This is why it's important to have a well-documented change control process.

#### Downtime
- Services will eventually be unavailable
	- Make changes during non-production hours
- If possible, prevent any downtime, switch to a secondary system if necessary
	- Should be automated as much as possible
	- Should be part of backout plan
- Send emails & updates to users

#### Restarts
Might need to implement a new configuration
- Reboot OS, power cycle the switch, bounce the service
For services, it's relatively quick, we can use task manager

For apps, just close and relaunch

#### Legacy applications
- Some apps have been around for a long time, often not even being supported by the developer
- Fear of the unknown, no one understands it
- Become the expert! Conquer the quirks

#### Dependencies
- To complete A, must first complete B.
- Modifying one component may require changing / restarting other components.
- Dependencies may occur across systems
	- Update firewall code first.

#### Documentation
- Often required with the change management process
- Includes updating diagrams, address updates
- Updating policies / procedures

#### Version control
- Track changes to a file or configuration data over time.
	- Router configs
	- Windows OS patches
	- Application registry entries
- May require additional management software if OS doesn't have it.
