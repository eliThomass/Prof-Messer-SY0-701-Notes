#### Serverless architecture

		- Each smaller app function can run in whatever OS happens to be appropriate
- Developer still creates the server side logic
	- Runs in a stateless compute container
- May be event triggered and ephemeral
- Managed by a third-party
	- All OS security conerns are at the third party
#### Microservices and APIs

	- Lets not do this, see below!

	- API is the glue for the microservices
	- Work together to act as the application
	- Scalable, Resilient, and Secure
		- Outages are contained

## Network Infrastructure Concepts
#### Physical Isolation
- Devices are physically separate
	- There is an air gap between them
- Must be connected to provide communication
- Web servers in one rack, all database servers in another rack air gap prevents them from communicating to each other
- Customer A on one switch, Customer B on another different switch.
#### Logical Segmentation with VLANs
- VLANs can separate switches logically instead of physically
#### Software Defined Networking (SDN)
- Networking devices have different functional planes of operation
	- Data, control, and management planes
- Split the functions into separate logical units
- **Data Plane**
	- Processes the network frames and packets
	- Forwarding, trunking, encrypting, NAT
- **Control Plane**
	- Manages the actions of the data plane
	- Routing tables, session tables, NAT tables
	- Dynamic routing protocol updates
- **Management Plane**
	- Configure and manage the device
	- SSH, browser, API

## Other Infrastructure Concepts
#### Attacks can happen anywhere
- Two categories for IT security
	- **On-premises data** is more secure!
	- Cloud-based data is more secure!
- Cloud-based security is centralized and costs less
	- No dedicated hardware, no data center to secure
- On-premises puts the security burden on the client
#### On-premises security
- Customize your security posture, you have full control
- On-site IT team can manage security better
- Local team maintains uptime/availability
- Security changes can take time
#### Centralized vs Not
- Most orgs are physically decentralized
	- Difficult to manage and protect so many diverse systems
- A centralized approach
	- Correlated alerts
	- Consolidated log file analysis
	- Comprehensive system status
		- Not perfect as it is a single point of failure
#### Virtualization
- Run many different operating systems on the same hardware
- Each app instance has its own operating system
- Infrastructure -> Hypervisor -> VMs with OS' and Apps
#### Application Containerization
- **Container**
	- Contains everything you need to run an app
	- Code & dependencies
	- A standardized unit of software
- Only thing the container needs is an OS to run on
- An isolated process is a sandbox, they are self-contained and can't interact w/ each other
- A **container image**
	- A standard for portability
	- Lightweight, uses the host kernel

#### SCADA / ICS
- Supervisory Control and Data Acquisition System
	- AKA Industrial Control System
- PC manages equipment
	- Power generation, refining, manufacturing equipment
- Distributed control systems
	- Real time info
	- System control
	- Operators sit in rooms looking at these
- Requires extensive segmentation, no outside access
- Some of the most secure systems in the world
#### RTOS (Real time OS)
- An operating system with a determinsitic processing schedule
	- No time to wait for other processes
	- Industrial equipment, automobiles, Military environments
- Extremely sensitive to security issues
	- Non-trivial systems, need to always be available
#### Embedded Systems
- Hardware/software designed for a specific function
- Built for one sole purpose
- Traffic light controllers, digital watches, medical imaging systems
#### High Availability
- Redundancy doesn't always mean always available
	- May need to be powered on manually
- HA = always on, always available
- May include many different components working together
	- Active/Active can provide scalability advantages

## Infrastructure Considerations
#### Availability
- System uptime
- Balancing act with security
	- Available but only to right people
- Lots of money spent on availability
- An important metric
	- We are often evaluated on total available time (99% uptime)
#### Resilience
- Eventually some shit goes down
	- Can you maintain availability? Recover? Quickly?
- Based on many different variables
	- Root cause, replacement hardware, software patch... etc
- Commonly referenced as ***MTTR***: Mean time to repair
#### Cost
- How much money required? Initial installation, tax implications, ongoing maintenance
#### Responsiveness
- Request info, get a response, how quickly?
- Important for interactive apps
- Speed is an important metric, all parts of app contribute to this
#### Scalability
- How quickly and easily can we inc/dec capacity? **Elasticity**
- There's always a resource challenge, costs lots of money
- Needs to include security monitoring
	- Increases/decreases as system scales
#### Ease of Deployment
- An app has many moving parts
- Might be an involved process
- Can be simple with cloud infrastructure
- Important to consider during the product engineering phase
#### Risk transference
- Many methods to minimize risk
	- Transfer the risk to a third-party
- Cybersecurity insurance
	- Recover internal losses during downtime from attacks
	- Protect against legal issues from customers
		- Help with costs associated with legal proceedings
#### Ease of recovery
- Something will eventually go wrong
	- Time is money
- Malware infection can take an hour or more, or just minutes
#### Patch availability
- Software not static
- Make sure you are running latest version
- Most companies have regular updates
- Some companies rarely patch
#### Inability to patch
- Embedded systems
- Not designed for end-user updates
- Get additionally security controls around the device. like a firewall
#### Power
- Yup we need it!
- Bring in licensed electrician for power usage and extension
- Primary power provider for most orgs
- Backup services (UPS [uninterruptible PS], generators)
#### Compute
- An apps heavy lifting
- The compute engine
	- Cloud term for it
- Might be a single processor or multiple CPUs across clouds
	- Enhanced scalability
