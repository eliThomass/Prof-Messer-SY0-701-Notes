#### High availability
- Redundancy doesn't always mean always available
- Might need to be powered on manually
- **HA (High Availability)** = always on, always available
- Many include many different components working together
- Also means higher costs
#### Server clustering
- Combine two or more servers to operate as one large server
- Users just see one device
- Easily increase capacity and availability
- Usually configured in the same operating system
#### Load balancing
- Load distributed across multiple servers
	- Servers unaware of each other, unlike clustering
- Distribute load across all the individual devices
- Load balancer adds or removes devices to increase capacity or if any servers aren't working
#### Site resiliency
-  Recovery site is prepped
- A disaster is called
- Problem is addressed
- Revert back to primary location
#### Hot site
- An exact replica of everything in your data center
- Stocked w/ hardware that is constantly updated
- Apps and software are constantly updated
- Flip and switch and everything moves, the service is fully back up in case the main data center is destroyed
#### Cold site
- An empty building w/ no hardware
- No data, so bring it with you
- No people, bus in your team
#### Warm site (tf?)
- Some equipment is on the secondary site
#### Geographic dispersion
- These sites should be physically different than the org's primary location
- Can be a logistical challenge such as transporting equipment/employees
	- Eventually this all needs to come back to main site if temporary
#### Platform diversity
- Every operating system contains potential security issues
- Many security vulnerabilities are specific to a single OS
- Use many different platforms
	- Harder to manage
#### Multi-cloud systems
- Plan for cloud outages
- Data is both geographically dispersed and cloud service dispersed
	- Plan for EVERY CONTINGENCY
#### Continuity of operations planning (COOP)
- Failback method if disasters cause disruption to the norm
- Must be an alternative to technology
	- Manual transactions
	- Paper receipts
	- Phone calls for transaction approvals
- Must be documented and tested before a problem occurs

## Capacity Planning
- Match supply to the demand
- Too much demand = app slowdowns and outages
- Too much supply = over spending
- Requries a balanced approach
	- Best infra, appropraite tech, approrpiate number of people
#### People
- Some services require human intervention
- Tech services
- Call center support lines
- Too few employees = recruit new staff
- Too many employees = redeploy to other parts of organization
#### Technology
- Pick a tech that can scale
- Web services should have an implementation with load balancers and servers for scalability
- Database services we should have multiple SQL servers we can enable
	- Split the database to increase capacity
- Cloud services
	- Services on demand
	- Seemingly unlimited resources (for enough money)
#### Infrastructure
- The underlying framework
	- App servers, net services, etc.
	- CPU, network, storage
- Physical devices
	- Purchase, config, install
- Cloud based devices
	- Easier to deploy

## Recovery Testing
- Test yourselves before an actual event
- Use well-defined rules of engagement
	- Do not touch the prod systems
- Very specific scenario, limited time to run the event
- Evaluate response, document, discuss
#### Tabletop exercises
- Many of the logistics can be determined through analysis
- Get key players together for a tabletop exercise
	- Talk through a simulated disaster
#### Fail over
- A failure is often inevitable
- We may be able to keep running
- To do this, create a redundant infrastructure
	- Multiple routers, firewalls, switches
- If one stops working, fail over to the operational unit
#### Simulation
- Test with a simulated event
	- Phishing attack, password requests
- Going phishing
	- Create phishing attack and send to everyone in the company
	- See who bites
- Test internal security
	- Did the phishing email get past our security?
- Test users
#### Parallel Processing
- Split a process through multiple CPUs
	- Single computer with multiple CPU cores
	- Multiple computers
- Improved performance
	- Complete transactions much more effeciently
- If one core fails, we can divert to another core / cpu

## Backups
- Many different implementations
	- Total amount of data
	- Type of backup
	- Storage location
	- Backup/recovery software
	- Backup schedule
#### Onsite vs. Offsite backups
- **On site backups**
	- No internet link needed
	- Less expensive generally
- **Off site backups**
	- Transfer data over Internet
	- Data is available after a disaster
- Organizations often use *both*
	- More copies of data, more disaster planning
#### Frequency
- May be different between systems
- May have multiple backup sets
	- Daily, weekly, monthly
- Requires lots of planning, there is a lot of media to manage
#### Encryption
- A history of *all* the data is on backup media
	- So we should protect that against attackers
	- Use encryption!
- Especially useful for cloud backups and storage
#### Snapshots
- Became popular on VMs and cloud infrastructures
- Take a snapshot
	- An instant backup of an entire system
	- Save the current configs and data, too
- Take another snapshot every 24 hours
#### Recovery Testing
- Not enough to perform backup
	- You need to also *verify* that you can restore them
- Disaster recovery testing
	- Simulate a disaster
	- Restore from backup
- Confirm the restoration
	- Test the restored app and data
- Perform periodic audits
	- Always have a good audit
#### Replication
- An ongoing, almost real-time backup stored in multiple locations
- Data is available, even files you just changed will have a copy
- Data can be stored locally to all users
- Data is recoverable
#### Journaling
- Power goes out while writing data to storage
	- Stored data is probably corrupted
- Recovery from this is complicated
	- Remove corrupted files, restore from backup
- Make a **journal entry**
	- Write data to journal, then copy that data into the database.
	- After the journal is written, write the data to storage
	- Now if the power went out, the journal would be lost, but the DB isn't corrupted.
- What if power goes out while data is being written from journal?
	- Then the DB can look to the journal to re-do the actions and uncorrupt the data.
- After data is written to storage, delete everything in journal and start the process again.

## Power Resiliency
- Power is the foundation of our technology
	- We must plan for outages
- We can't control power availability
- Design and develop systems to allow for some level of access to electricity
#### UPS (Uninterruptible Power Supply)
- Short-term backup power
- **Blackouts, brownouts (drop in voltage), surges (excessive voltage)**
- UPS types
	- Offline/standby UPS
		- Turns on only if power cuts out
	- Line-interactive UPS
		- Increases voltage if it sees a drop in voltage on the power line
	- On-line UPS
		- If you switch between main power and battery power a lot
- Features: auto shutdown, battery capacity, outlets, phone line suppression
#### Generators
- Long term power backup
	- Fuel is needed
- Power an entire building or a section of outlets inside a building
- Takes a few minutes to get up to speed, so use a UPS while it starts
